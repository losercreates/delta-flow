# Feature Specification: Production Packaging & Real-Time Observability Stack

**Feature Branch**: `007-production-packaging`  
**Created**: 2026-11-17  
**Status**: Draft  
**Input**: User description: "Production Packaging & Observability: Implement a unified multi-container docker-compose stack with PostgreSQL 16, Redis 7, DeltaFlow Backend, and Vite Frontend Dashboard. Configure OpenTelemetry OTLP exporter to stream virtual thread W3C traces to a Jaeger/OTLP collector container, expose custom Micrometer metrics via Spring Boot Actuator (/actuator/prometheus), and provide pre-provisioned Prometheus and Grafana dashboards for real-time monitoring of saga throughput, step latency, lock contention, and idempotency cache hit rates. Include one-command startup/teardown automation and a health verification smoke script."

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 - One-Command Multi-Container Production Stack (Priority: P1) 🎯 MVP

As a DevOps engineer, system administrator, or developer, I want a unified, production-ready containerization specification orchestrating the entire DeltaFlow platform (PostgreSQL 16, Redis 7, DeltaFlow Spring Boot Backend, and React/Vite Operator Dashboard) with declarative health checks, persistent volumes, environment configuration, and strict startup sequencing, so that I can bring up the complete operational ecosystem in a single command (`docker compose up -d`) in under 60 seconds with zero manual configuration.

**Why this priority**: Core foundation for all local development, staging deployments, and customer demonstrations. Without deterministic multi-container orchestration, setting up and running DeltaFlow requires manual installation of multiple stateful services, configuring ports, and managing separate terminal sessions.

**Independent Test**: Can be validated by executing `docker compose up -d` on a clean host machine. All containers transition to healthy status, database migrations execute automatically on startup, the frontend dashboard connects to the backend proxy, and an API transfer request submitted to `http://localhost:8080/api/v1/transfers` completes successfully with terminal status recorded in PostgreSQL.

**Acceptance Scenarios**:

1. **Given** a clean machine with Docker and Docker Compose installed, **When** the operator executes `docker compose up -d`, **Then** PostgreSQL 16 and Redis 7 start, execute internal health probes (`pg_isready` and `redis-cli ping`), and report `healthy` before the backend container attempts to boot.
2. **Given** healthy database and cache services, **When** the DeltaFlow backend container initializes, **Then** Flyway automatically applies all database migrations, Spring Boot activates the production profile with Java 21 preview features enabled, and the Actuator health endpoint reports status `UP`.
3. **Given** a running backend, **When** the operator dashboard container starts, **Then** it serves the UI on port 3000 and seamlessly proxies `/api` calls to the backend on port 8080 without Cross-Origin Resource Sharing (CORS) errors.
4. **Given** data written to PostgreSQL and Redis during runtime, **When** the stack is stopped (`docker compose stop`) and restarted (`docker compose start`), **Then** all historical saga records, audit events, and idempotency keys persist intact via named Docker volumes.
5. **Given** an active production stack processing transfers, **When** the operator issues a termination command (`docker compose down`), **Then** the backend container receives `SIGTERM`, initiates graceful draining within the 30-second window, and completes in-flight database transactions before stopping.

### User Story 2 - End-to-End Distributed Trace Visualization with Jaeger & OTLP (Priority: P1)

As a Site Reliability Engineer (SRE), production support engineer, or developer, when transactions execute, fail, or trigger backward compensations, I want distributed W3C traces generated by DeltaFlow to be automatically exported via OpenTelemetry Protocol (OTLP) to a bundled Jaeger / OpenTelemetry Collector service, so that I can inspect complete waterfall timelines across virtual threads, database queries, and parallel branch executions in the Jaeger UI.

**Why this priority**: Non-negotiable observability requirement (Constitution Principle V: Observability & Immutable Audit Trail). Complex distributed transactions spanning virtual threads, parallel step execution, and backward compensations cannot be diagnosed under failure without synchronized distributed trace waterfalls.

**Independent Test**: Can be validated by executing a multi-step financial transfer through the API, then opening the Jaeger UI at `http://localhost:16686`. The trace search returns the transaction's trace record containing correlated spans for the HTTP controller, idempotency lock acquisition, WAL step recording, outbound service calls, outbox event generation, and any compensation spans.

**Acceptance Scenarios**:

1. **Given** a financial transfer request submitted with or without an existing W3C `traceparent` header, **When** processed by the backend, **Then** all internal spans (step execution, outbox persistence, lock handling) are automatically streamed via OTLP (gRPC or HTTP) to the Jaeger collector container.
2. **Given** an executed saga, **When** an operator navigates to the Jaeger UI (`http://localhost:16686`) and searches by service name `delta-flow`, **Then** the search displays traces tagged with searchable attributes including `sagaId`, `tenantId`, `idempotencyKey`, and `stepName`.
3. **Given** a saga step utilizing Java 21 Structured Concurrency with parallel branches, **When** inspected in the trace waterfall, **Then** child branch spans appear chronologically nested under the parent parallel step span with accurate individual start times and durations.
4. **Given** a transaction failure triggering backward compensation, **When** viewed in the trace viewer, **Then** the failed forward span is marked with error metadata and the compensating spans are linked to the same root trace, clearly distinguishing forward actions from rollback actions.

### User Story 3 - Real-Time Operational Metrics with Prometheus & Pre-Provisioned Grafana (Priority: P2)

As a Platform Operations Lead or SRE, I want DeltaFlow to expose rich domain and infrastructure metrics via Spring Boot Actuator (`/actuator/prometheus`) scraped by Prometheus, visualized on a pre-provisioned, production-ready Grafana dashboard, so that our team has immediate, out-of-the-box visibility into transaction throughput, p50/p95/p99 saga execution latencies, distributed lock contention, step failure rates, and idempotency cache hit ratios without configuring dashboards manually.

**Why this priority**: Essential for production capacity planning, Service Level Objective (SLO) tracking, and real-time incident alerting. Operators require instant visibility into system saturation and failure rates.

**Independent Test**: Can be validated by launching the stack and accessing Grafana at `http://localhost:3001`. The pre-configured "DeltaFlow Overview & Financial Reliability" dashboard displays live metric gauges, time-series graphs, and counters populated with data scraped from the running backend.

**Acceptance Scenarios**:

1. **Given** the running DeltaFlow backend, **When** Prometheus queries `/actuator/prometheus` at regular scrape intervals (e.g., 5s), **Then** Prometheus successfully ingests both standard JVM/system metrics and custom DeltaFlow domain metrics.
2. **Given** incoming traffic containing both unique requests and duplicate replays, **When** monitored in Prometheus/Grafana, **Then** the metric `deltaflow_idempotency_requests_total` accurately tracks counts partitioned by status tags (`direct`, `cached`, `conflict`).
3. **Given** multi-step saga executions, **When** monitored in Prometheus/Grafana, **Then** the timer metric `deltaflow_saga_duration_seconds` provides accurate percentiles (p50, p95, p99) broken down by saga definition name and outcome (`COMPLETED`, `COMPENSATED`, `FAILED`).
4. **Given** distributed lock acquisition across Redis and PostgreSQL fallback, **When** contending requests arrive, **Then** the metric `deltaflow_lock_acquisition_seconds` measures lock acquisition latency and contention duration.
5. **Given** a freshly booted stack, **When** opening Grafana on port 3001, **Then** Grafana requires no manual setup: the Prometheus and Jaeger datasources and the DeltaFlow operational dashboard are already provisioned and functional.

### User Story 4 - Turnkey Automation, Health Smoke Verification & Diagnostic Tooling (Priority: P3)

As a developer, QA engineer, or CI/CD automation pipeline, I want automated command-line control scripts and a comprehensive health smoke-verification utility, so that I can validate that every container, database migration, metrics scraper, and trace exporter is fully functional in a single execution.

**Why this priority**: Reduces mean-time-to-detection for deployment regressions, accelerates onboarding for new engineers, and provides a standardized sanity check for automated CI/CD staging environments.

**Independent Test**: Can be validated by running a single smoke verification script (e.g., `./scripts/smoke-test.sh` or `make smoke`). The script verifies container health states, submits test transactions (happy path, cached replay, tampering detection, and compensation), queries Prometheus for scraped metrics, verifies trace existence in Jaeger, and outputs a structured pass/fail report in under 15 seconds.

**Acceptance Scenarios**:

1. **Given** a running Docker Compose environment, **When** the operator runs the smoke verification utility, **Then** the script verifies that all expected containers (`deltaflow-db`, `deltaflow-redis`, `deltaflow-backend`, `deltaflow-frontend`, `jaeger`, `prometheus`, `grafana`) report healthy status.
2. **Given** healthy services, **When** the smoke test executes scenario 1 (Direct Payment), **Then** it receives `HTTP 201 Created` with header `Idempotency-Status: DIRECT`.
3. **Given** the completed transaction from scenario 1, **When** the smoke test executes scenario 2 (Idempotent Replay), **Then** it receives `HTTP 201 Created` with header `Idempotency-Status: CACHED` in under 20ms with identical transaction ID.
4. **Given** the same key with an altered amount, **When** the smoke test executes scenario 3 (Payload Tampering), **Then** it receives `HTTP 409 Conflict` with error code `IDEMPOTENCY_KEY_PAYLOAD_MISMATCH`.
5. **Given** an intentionally failing step, **When** the smoke test executes scenario 4 (Compensation), **Then** it verifies that backward compensation completes and the saga status resolves to `COMPENSATED`.
6. **Given** all scenarios executed, **When** the smoke script polls Prometheus and Jaeger, **Then** it confirms that metrics have incremented and traces have been indexed for the generated transaction IDs.

### Edge Cases

- **Slow Database Initialization**: If PostgreSQL takes longer than usual to complete initial data directory initialization, the backend container's health dependency policy (`condition: service_healthy`) must hold backend startup until the PostgreSQL socket is accepting connections.
- **Redis Connection Drops or Restarts**: If Redis restarts while the backend is running, Redisson and Spring Data Redis must automatically reconnect without restarting the backend process.
- **OTLP Exporter Backpressure & Buffer Saturation**: If the Jaeger or OpenTelemetry collector container is temporarily stopped or overloaded, the backend OTLP exporter must drop or buffer spans asynchronously without blocking caller virtual threads or increasing transaction latency.
- **Port Conflicts on Host Machine**: If standard host ports (5432, 6379, 8080, 3000, 9090, 3001, 16686) are already bound on the host machine, all ports must be cleanly overridable via an environment configuration file (`.env`) without editing the compose file.
- **Prometheus Scraping During Graceful Shutdown**: When the backend receives a `SIGTERM` and enters graceful shutdown, the readiness probe transitions to `OUT_OF_SERVICE`. Prometheus must record the status change without crashing or marking the target permanently dead.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST provide a multi-container specification (`docker-compose.yml`) orchestrating seven distinct services: PostgreSQL 16, Redis 7, DeltaFlow Backend, Operator Dashboard Frontend, Jaeger (with OTLP receiver), Prometheus, and Grafana.
- **FR-002**: Database and caching services MUST define declarative container health checks (`pg_isready -U postgres` and `redis-cli ping`), and dependent application services MUST enforce startup ordering via `condition: service_healthy`.
- **FR-003**: System MUST define named Docker volumes for PostgreSQL data (`deltaflow-db-data`), Redis data (`deltaflow-redis-data`), Prometheus time-series data (`prometheus-data`), and Grafana storage (`grafana-data`) ensuring state persistence across container teardown and recreation.
- **FR-004**: System MUST provide a production containerization build definition (Dockerfile) for the Spring Boot backend using a multi-stage build (build stage + minimal JRE 21 runtime stage) with Java 21 preview features (`--enable-preview`) enabled for Virtual Threads.
- **FR-005**: System MUST provide a containerization build definition (Dockerfile) for the frontend dashboard using a lightweight web server (Nginx or Node Vite server) proxying API requests to the backend.
- **FR-006**: System MUST configure the OpenTelemetry OTLP exporter to transmit spans generated by `DeltaFlowTracer` to the Jaeger/OTLP endpoint over gRPC (port 4317) or HTTP (port 4318) using an environment variable (`OTEL_EXPORTER_OTLP_ENDPOINT`).
- **FR-007**: System MUST instrument and publish core operational domain metrics via Spring Boot Actuator and Micrometer:
  - `deltaflow.idempotency.requests`: Counter measuring incoming idempotency evaluations tagged by outcome (`direct`, `cached`, `conflict`, `locked`).
  - `deltaflow.saga.duration`: Timer recording end-to-end saga execution durations with p50, p95, and p99 percentiles, tagged by saga definition and terminal status (`COMPLETED`, `COMPENSATED`, `FAILED`).
  - `deltaflow.saga.steps.active`: Gauge recording currently executing forward or compensating steps.
  - `deltaflow.saga.steps.total`: Counter recording step transitions tagged by step name and outcome (`COMPLETED`, `COMPENSATED`, `FAILED`).
  - `deltaflow.lock.acquisition.time`: Timer measuring time taken to acquire distributed locks in Redis or PostgreSQL.
  - `deltaflow.compensations.total`: Counter recording total backward compensation workflows initiated.
- **FR-008**: System MUST configure Prometheus with a scrape target configured to collect metrics from the backend's `/actuator/prometheus` endpoint at a 5-second sampling interval.
- **FR-009**: System MUST pre-provision Grafana configuration including:
  - Datasources: Prometheus (`http://prometheus:9090`) and Jaeger (`http://jaeger:16686`).
  - Dashboard Provider: Automatically loading a pre-built JSON dashboard ("DeltaFlow Operational Reliability") upon startup with zero manual UI configuration.
- **FR-010**: System MUST provide an environment configuration template (`.env.example` / `.env`) allowing operators to customize database credentials, host port mappings, memory limits, and log levels.
- **FR-011**: System MUST provide an automated health smoke verification script (`scripts/smoke-test.sh` and Makefile targets) that performs container health checks, executes end-to-end API verification scenarios, and verifies metrics/trace ingestion.

### Key Entities *(include if feature involves data)*

- **Container Stack Configuration**: Specification defining service dependencies, network topologies (`deltaflow-network`), volume mounts, resource constraints, and health probe intervals.
- **OTLP Trace Export Pipeline**: Asynchronous span batching pipeline transmitting W3C-correlated spans from the JVM runtime to the OpenTelemetry collector.
- **Operational Metrics Registry**: Set of Micrometer counters, gauges, and distribution summaries capturing real-time transaction throughput, latency percentiles, and lock contention.
- **Provisioned Dashboard Definition**: Declarative JSON artifact detailing Grafana panels, PromQL queries, thresholds, and Jaeger trace-to-metric drill-down links.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: The entire 7-service stack boots from an initial clean state to fully healthy and operational status with a single command (`docker compose up -d`) in under 60 seconds.
- **SC-002**: 100% of executed transactions generate visible, fully correlated W3C trace waterfalls in the Jaeger UI within 3 seconds of transaction completion.
- **SC-003**: Custom operational metrics (idempotency outcomes, saga durations, lock latencies) appear on the pre-provisioned Grafana dashboard within 10 seconds of initial request execution with zero manual dashboard configuration.
- **SC-004**: Stopping the stack (`docker compose down`) performs a clean drain of active transactions within the 30-second graceful shutdown window, resulting in zero corrupted database states or stranded locks.
- **SC-005**: The automated health smoke verification script executes all four core validation scenarios (direct payment, cached replay, tampering detection, and compensation) and confirms metrics/traces in under 15 seconds with a 100% pass rate.
- **SC-006**: Changing host port mappings via `.env` enables running the entire stack on alternative ports without any manual edits to container definitions.

## Assumptions

- The host environment has Docker Engine (v20.10+) and Docker Compose (Compose v2) installed and running.
- The host system provides sufficient resources to run all seven containers simultaneously (minimum 4 CPU cores and 4GB available RAM recommended).
- Java 21 preview features (`--enable-preview`) are supported and enabled within the backend container's runtime environment.
- Default ports (5432 for Postgres, 6379 for Redis, 8080 for Backend, 3000 for Frontend, 9090 for Prometheus, 3001 for Grafana, 16686 for Jaeger UI, 4317/4318 for OTLP) are available or can be remapped via `.env`.
- Internal container networking utilizes an isolated bridge network (`deltaflow-network`) allowing DNS service discovery between containers (e.g., `http://deltaflow-backend:8080`).
